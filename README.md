# adl200a-mqtt

Небольшой надёжный **systemd-сервис** для Linux: опрашивает геотехнический
даталоггер **ACE Instrument ADL-200A** по RS-232 и публикует показания в локальный
**MQTT**-брокер в формате JSON.

Протокол ADL-200A недокументирован и проприетарен — он был реверс-инжинирен из
фирменной программы `ADL2Pro.exe` и подтверждён на живом железе. Полное описание —
в **[PROTOCOL.md](PROTOCOL.md)**.

## Установка из deb без интернета

Пакет для UVON / Astra включает pyserial и paho-mqtt, подтверждённую доставку
MQTT QoS 1 и постоянные логи на 14 дней. Для полного офлайн-комплекта системные
зависимости скачиваются на той же версии ОС и архитектуре, что и целевой аппарат.
Команды установки, ограничения совместимости и сборка:
**[packaging/README.md](packaging/README.md)**.

## Что делает

- Держит постоянное соединение с портом (с автопереподключением).
- Раз в `ADL200A_INTERVAL` секунд шлёт `MEA` (измерение включённых каналов; длительность зависит от прибора и числа каналов).
- Разбирает покадровый ответ `MES` и публикует JSON в MQTT.
- Пишет лог в `stdout` (под systemd — в journald).

## Железо

Хост-порт логгера — **RS-232, 38400 8N1**. Две проверенные конфигурации:

| Хост | Адаптер | Устройство | Примечания |
|------|---------|-----------|------------|
| x86 ПК (напр. Dell Wyse) | Moxa UPort 1150 (USB↔RS-232) | `/dev/ttyUSB0` | нужна прошивка `moxa/moxa-1150.fw` (`firmware-misc-nonfree`) и драйвер целевой ОС; на Wyse проверен `ti_usb_3410_5052`; RS-232-режим сервис ставит сам |
| ARM SBC (напр. UVON) | нативный UART SoC через RS-232-трансивер | `/dev/ttyS0`, … | работает из коробки, драйверов не надо |

> RS-232 — точка-точка: логгер общается с одним хостом за раз.

## Установка

```sh
sudo ./install.sh
sudo nano /etc/default/adl200a        # указать ADL200A_PORT — свой порт
sudo systemctl enable --now adl200a
```

`install.sh` ставит зависимости (`python3-serial`, `python3-paho-mqtt`,
`mosquitto`), копирует файлы в `/opt/adl200a`, кладёт конфиг
`/etc/default/adl200a` и регистрирует сервис.

### Запуск на UVON (ARM, нативный RS-232)

Драйверов не нужно — UART SoC уже является RS-232-портом.

```sh
# 1. установка (зависимости + файлы + сервис)
sudo ./install.sh

# 2. указать порт, к которому подключён ADL-200A (ttyS0, ttyS1, …)
sudo sed -i 's#^ADL200A_PORT=.*#ADL200A_PORT=/dev/ttyS0#' /etc/default/adl200a

# 3. запустить и включить автозапуск
sudo systemctl enable --now adl200a

# 4. смотреть лог
journalctl -u adl200a -f
```

Проверить, что логгер отвечает (сервис держит порт монопольно — сначала остановить):

```sh
sudo systemctl stop adl200a
ADL200A_PORT=/dev/ttyS0 python3 /opt/adl200a/ace.py GTT     # должен вернуть время
sudo systemctl start adl200a
```

> Если `ttyS*` на плате — это **TTL-UART 3.3 В** (гребёнка), а не полноценный RS-232
> (±12 В на трансивере), напрямую к логгеру подключать нельзя — нужен модуль
> **MAX3232** между UART и RS-232 логгера.

## Конфигурация — `/etc/default/adl200a`

| Переменная | По умолчанию | Значение |
|-----------|--------------|----------|
| `ADL200A_PORT` | `/dev/ttyUSB0` | последовательный порт логгера |
| `ADL200A_BAUD` | `38400` | скорость |
| `ADL200A_ID` | `1` | Logger ID |
| `ADL200A_INTERVAL` | `100` | секунд между циклами измерения |
| `ADL200A_MEA_MAX_SECONDS` | `90` | максимальное время ожидания полного ответа MEA |
| `ADL200A_MEA_IDLE_DONE` | `20` | секунд тишины для завершения MEA, если состав каналов неизвестен |
| `ADL200A_MQTT_HOST` / `_PORT` | `127.0.0.1` / `1883` | MQTT-брокер |
| `ADL200A_TOPIC` | `adl200a` | префикс MQTT-топиков |
| `ADL200A_SENSORS` | `/etc/adl200a/sensors.json` | калибровки датчиков (см. ниже) |
| `ADL200A_PENDING_FILE` | `/var/lib/adl200a/pending.json` | один ответ, ожидающий подтверждения MQTT |
| `ADL200A_MQTT_CLIENT_ID` | `adl200a-<hostname>-<id>` | уникальное имя клиента на брокере |

После правки конфига: `sudo systemctl restart adl200a`.

### Подтверждённая доставка без базы данных

Полученный цикл атомарно записывается в один временный файл очереди. Все MQTT-сообщения
отправляются с QoS 1; файл удаляется только после PUBACK для каждого сообщения.
При разрыве связи повторная отправка выполняется автоматически. Пока ответ ожидает
подтверждения, новые команды измерения не отправляются: очередь и память не растут.
После перезапуска сначала доставляется сохранённый ответ, затем продолжается опрос.
Это очередь доставки, а не архив измерений. Удалённый после подтверждения ответ
сервис не хранит.

Каждый цикл и JSON отдельного канала содержат `cycle_id`. QoS 1 допускает повторы,
особенно при перезапуске до удаления файла; получатель может исключать их по этому ID.
PUBACK подтверждает приём MQTT-брокером. Для подтверждения обработки конечным
потребителем нужен отдельный ответ от этого потребителя.

`complete=true` означает, что получены все настроенные входы (по `GCC`: `t01`, `t06` и т. д.) всех ожидаемых каналов с одним
временем измерения прибора. При тайм-ауте передаются собранные данные с
`complete=false`, `missing_channels` и `end_reason`. Если GCC ещё не прочитан,
`complete=null`: полнота неизвестна. Известный набор каналов ожидается до общего
лимита MEA, промежуточная тишина его не обрезает. Таймеры используют монотонные часы.
При повторном открытии RS-232 конфигурация GCC читается заново; порт открывается
монопольно. Новая установка создаёт пустую калибровку, пример не включается автоматически.

## Как забрать данные из сервиса

Демон публикует в локальный MQTT-брокер (mosquitto). Забрать может что угодно,
что умеет MQTT: дашборд, Node-RED, Home Assistant, Telegraf/InfluxDB или свой
скрипт.

### Какие каналы приходят

Каждый цикл шлёт `MEA`. Логгер опрашивает **только те каналы, что включены в его
собственной конфигурации**, — посмотреть её можно командой `GCC`:

```
<<!01,01,GCC:02,1,1,1,0020,6;   <- канал включён
<<!01,01,GCC:03,0,0,0,0000,0;   <- канал выключен, в MEA его не будет
```

Ответ на `MEA` приходит **канал за каналом с паузами в несколько секунд**, поэтому
«давно нет данных» — плохой признак конца развёртки: он режет её пополам, и остаток
всплывает в следующем цикле (в журнале это видно как `Published 1 channels` через
раз). Сервис спрашивает `GCC` при старте и ждёт ровно включённые каналы:

```
Logger sweeps channels 02, 04
Published 2 channels (196 raw bytes)
```

### Настройка каналов прибора — `channels.py`

Какие каналы опрашивать и что на них подключено, решает сам прибор. У каждого
канала два входа — **струнный (VW)** с полосой развёртки и **аналоговый** с типом
датчика; полный разбор полей — в [PROTOCOL.md](PROTOCOL.md). Желаемое состояние
описывается в том же `/etc/adl200a/sensors.json`, что и калибровки (см. ниже), а
`channels.py` приводит прибор к файлу:

```sh
python3 /opt/adl200a/channels.py --show            # что сейчас в приборе
python3 /opt/adl200a/channels.py --apply           # сухой прогон: что поменяется
python3 /opt/adl200a/channels.py --apply --yes     # записать и сверить
```

```
канал  в приборе                                       по файлу
≠ 01   VW Sweep 01 (450–1200 Гц) + Thermistor 3K       VW Sweep 03 (1400–3500 Гц) + Thermistor 3K
≠ 02   VW Sweep 01 (450–1200 Гц) + Thermistor 3K       выключен (нет в файле)
...
  01: VW Sweep 01 (450–1200 Гц) + Thermistor 3K  →  VW Sweep 03 (1400–3500 Гц) + Thermistor 3K
  после: включено каналов 1, развёртка ≈ 5 с
  (сухой прогон) >>?1,1,SCC:1,1,1,3,20,6;
```

- Каналы, которых нет в файле, при `--apply` **выключаются** (`--keep-others` —
  не трогать): каждый лишний канал удлиняет развёртку примерно на 5 секунд.
- Ошибки в файле собираются все разом, и тогда прибор не трогается вовсе.
- Порт занят службой — инструмент останавливает её сам и возвращает на выходе, в
  том числе при ошибке (`--no-service`, чтобы не трогал).
- Без `--yes` в прибор ничего не пишется. Перед записью снимается копия
  конфигурации, вернуть как было:
  `channels.py --restore /var/lib/adl200a/gcc-backup.txt --yes`.

Ручная настройка, мимо файла — например, найти, к какому каналу подключён датчик.
Полосу здесь надо указать явно: по умолчанию её нет, потому что неверная полоса —
ровно та ошибка, из-за которой датчик не читается:

```sh
python3 /opt/adl200a/channels.py --enable-all --sweep 3 --yes
python3 /opt/adl200a/channels.py --only 1 --sweep 3 --analog thermistor_3k --yes
```

**Не держи включёнными лишние каналы.** Развёртка идёт по включённым каналам
последовательно, около 5 секунд на канал (два канала ≈ 6 с, тринадцать ≈ 70 с). На
полном наборе прибор занят почти всё время и **тормозит со служебными командами**:
`GCC` и `GTT` отвечают с задержкой в 20–30 секунд, ответы приезжают уже к
следующей команде. Инструмент к этому готов — ждёт, пока прибор замолчит,
принимает конфигурацию только целиком и различает «не применилось» и «не смог
проверить», — но лучше включить все каналы один раз для поиска и сразу вернуться
к рабочим через `--apply`.

### Что публикуется

- `adl200a/ch/NN` — по каналу (JSON);
- `adl200a/measurement` — весь цикл одним JSON;
- `adl200a/config` — **retained**: как настроен каждый включённый канал и что
  значит каждое сырое значение (`t01`, `t06`, …). Служба читает это из прибора
  (`GCC`) при старте, так что топик всегда отражает прибор, а не файл.

В MQTT идут **только сырые отсчёты прибора** — калибровка к ним не применяется,
чтобы ряд в базе не зависел от файла с коэффициентами, который потом могут
поправить. Пересчёт в инженерные единицы — для проверки глазами в консоли,
см. `live.sh` и `calibration.py` ниже.

Номер в ключе `tNN` — код типа входа, тот же, что в настройке канала: `t01` —
струнный датчик (Гц × 100), `t06` — термистор (омы, 3 кОм ≈ 25 °C), остальные —
mV, Bridge, Serial, Resistance, RTD (`calibration.py --types`). Оборванный канал
видно сразу: `t01 = 0`, а `t06` уходит далеко за 110 кОм.

## Калибровка — `/etc/adl200a/sensors.json`

Один файл описывает и то, как настроить прибор, и как пересчитать его отсчёты
(шаблон — [`sensors.example.json`](sensors.example.json)). По записи на канал:

```json
{"channels": {"01": {
  "name": "VW earth pressure cell", "model": "1910", "serial": "587968",
  "unit": "kgf/cm2", "range": 3.5,
  "sweep": "auto", "analog": "thermistor_3k",
  "cal_temp_c": 24.0, "initial_temp_c": null,
  "raw_unit": "hz_x100", "hz_min": 2280.4, "hz_max": 2991.4,
  "polynomial": {"A": -0.00000088515, "B": -0.000254190, "C": 8.68208},
  "linear": {"gage_factor": -0.00093328, "zero_reading": 8946.19},
  "thermal_coefficient": -0.00037901, "thermistor": "3k"}},
 "logger": {"recording": {"interval_min": 15, "mode": "fixed", "when_full": "overwrite"}}}
```

**Входы канала** — их записывает в прибор `channels.py --apply`:

| Поле | Значения |
|------|----------|
| `sweep` | `"auto"` — самая узкая полоса, целиком накрывающая `hz_min`…`hz_max` из сертификата; `1`–`4` — явно (проверяется, что полоса накрывает датчик); `null` — струнный вход не нужен |
| `analog` | `thermistor_3k`, `mv`, `bridge`, `resistance`, `rtd`, `serial` или `null` |
| `serial_count` | для `serial` — сколько значений отдаёт датчик |

Полосы: `1` — 450–1200 Гц, `2` — 800–2000, `3` — 1400–3500, `4` — 2400–6000. Ячейке
1910 (2280–2991 Гц) подходит только **Sweep 03**; Sweep 01, стоящая в приборе с
завода, её не накрывает вовсе. `bridge` и `serial` нельзя совмещать со струнным
входом на одном канале — так решил производитель. Оба поля обязательны: забытое
поле — ошибка, а не «вход выключен».

**`logger.recording`** — необязательный блок собственной записи логгера в его
память, независимой от опроса службой: интервал в минутах, режим `fixed` или
`periodic` (как в меню вендора), при заполнении памяти — `stop` или `overwrite`.
Без блока `--apply` эти настройки не трогает. Прибор с завода пишет **раз в
минуту**, и при многих каналах его собственная развёртка сталкивается с нашей.

**Калибровка** — всё остальное. Ею пользуются только **консольные инструменты**
(`live.sh` и `calibration.py`); сама служба калибровку не читает и в MQTT её не
подмешивает.

**Масштабы аналоговых входов** — mV, Bridge, Resistance, RTD, Serial — задаёт
установщик в блоке `analog_scale` канала: множитель «сырое целое → величина на
входе» (подбирается по эталону) и пересчёт — `linear`, `polynomial` или готовая
кривая `pt100`/`pt1000`. Как подобрать и примеры — в
[инструкции по подключению](docs/install-ace-1910.md#11-другие-датчики-mv-bridge-resistance-rtd-serial).
Проверить файл целиком: `calibration.py --check`.

**Пошаговая инструкция для установщиков** — от паспорта датчика до проверенных
показаний: [docs/install-ace-1910.md](docs/install-ace-1910.md).

Считается ровно по формулам сертификата:

- давление (основное) — `P = A·Hz² + B·Hz + C − Tct·(Tc − Ti)`;
- давление (линейная проверка) — `P = G·(digits − zero) − Tct·(Tc − Ti)`, `digits = Hz²/1000`;
- температура — Стейнхарт–Харт по термистору 3 кОм @ 25 °C:
  `1/T = 1.4051·10⁻³ + 2.369·10⁻⁴·lnR + 1.019·10⁻⁷·(lnR)³`.

`initial_temp_c` — температура на момент установки, от неё считается температурная
поправка; `null` означает «брать температуру калибровки».

### `raw_unit` — в каких единицах логгер отдаёт `t01`

Вендорское меню говорит, что струнный вход отдаёт частоту в Гц; на живом приборе
подтверждено **`hz_x100`** — `0000294720` = 2947,20 Гц. Поле всё же можно задать
явно (`hz`, `hz_x100`, `digits`, `digits_x10`) или поставить `"auto"`: тогда
консольные инструменты подбирают масштаб по паспортному окну `hz_min`…`hz_max` на
первом реальном отсчёте. Варианты различаются больше чем в 10 раз, так что
подходит всегда ровно один.
Посмотреть все разом:

```sh
python3 /opt/adl200a/calibration.py --explain 82233
python3 /opt/adl200a/calibration.py --channel 02 --raw 82233 --therm 2987
```

### Живая сессия в консоли — `live.sh`

Для настройки и установки датчиков: таблица в реальном времени, сырые отсчёты
рядом с инженерными величинами, в конце — сводка с размахом и дрейфом.

```sh
/opt/adl200a/live.sh                 # из MQTT, службу не трогает (раз в минуту)
/opt/adl200a/live.sh -d              # прямой опрос: цикл ~10 с вместо минуты
/opt/adl200a/live.sh -d -z -c 02     # только канал 02, Δ от первого отсчёта
/opt/adl200a/live.sh -d -r -l /tmp/установка.log   # + кадры протокола, с записью в файл
```

```
по файлу ch01: VW Sweep 03 (1400–3500 Гц) + Thermistor 3K  [полоса выбрана по сертификату]
в приборе ch01: VW Sweep 03 (1400–3500 Гц) + Thermistor 3K

   время  ch     VW t01  терм t06        Гц     digits     кгс/см²       кПа     %FSR       °C  статус
--------  --  ---------  --------  --------  ---------  ----------  --------  -------  -------  ------
10:27:59  01     294720      3344   2947.20     8686.0      0.2440     23.93    6.97%    22.53  ok
```

Сессия сверяет настройку прибора с файлом (в прямом опросе — по `GCC`, из MQTT — по
топику `adl200a/config`) и прямо говорит, если они расходятся, если включены
лишние каналы или если частота датчика вышла за полосу развёртки. Значения других
типов входов (mV, RTD и т.д.) выводятся в конце строки сырыми.

В режиме `-d` служба на время сессии останавливается и возвращается на выходе
(Ctrl-C или `-n N` строк) — иначе порт занят демоном. Полный список ключей:
`live.sh -h`.

Через ssh запускай с `-t`, иначе Ctrl-C оборвёт только ssh-клиент: сессия на плате
завершится сама (по обрыву трубы) и службу вернёт, но сводку на экране ты не
увидишь — её сохранит `-l ФАЙЛ`.

```sh
ssh -t astra '/opt/adl200a/live.sh -d -z -c 02'
```

### Из консоли

```sh
mosquitto_sub -h 127.0.0.1 -t 'adl200a/#' -v          # всё
mosquitto_sub -h 127.0.0.1 -t 'adl200a/ch/02' -v      # один канал
mosquitto_sub -h 127.0.0.1 -t 'adl200a/measurement' -v  # весь цикл
```

### Из кода (Python)

Готовый пример — [`examples/subscribe.py`](examples/subscribe.py):

```sh
python3 examples/subscribe.py                 # локально
python3 examples/subscribe.py 100.71.138.46   # с другого хоста (см. ниже)
```

### С другой машины

По умолчанию mosquitto слушает только `localhost`. Чтобы читать данные удалённо:
- запусти консьюмер на самом хосте логгера, **или**
- пробрось порт: `ssh -L 1883:127.0.0.1:1883 uvon-debian`, затем подключайся к
  `127.0.0.1:1883` у себя, **или**
- настрой в mosquitto внешний listener / bridge.

### Формат сообщения (топик `adl200a/ch/NN`)

```json
{"channel": 1, "values": {"t01": 294720, "t06": 3344},
 "dev_date": "26/09/30", "dev_time": "17:30:51",
 "timestamp": "2026-09-30T14:30:33+00:00"}
```

`t01` — струнный отсчёт, `t06` — сопротивление термистора в омах. Ничего больше
служба не добавляет; что значит каждый ключ на каждом канале — в retained-топике
`adl200a/config`:

```json
{"timestamp": "…", "logger_id": 1, "channels": [{"channel": 1,
  "setting": "VW Sweep 03 (1400–3500 Гц) + Thermistor 3K", "fields": [1, 1, 3, 20, 6],
  "vw": {"sweep": 3, "band_hz": [1400, 3500]},
  "analog": {"code": 6, "type": "thermistor_3k", "label": "Thermistor 3K"},
  "values": {"t01": {"input": "vw", "unit": "Hz x100"},
             "t06": {"input": "thermistor_3k", "unit": "Ohm"}}}]}
```
 Посмотреть, во что это превращается, можно в консоли:

```sh
/opt/adl200a/live.sh                                   # живая таблица
python3 /opt/adl200a/calibration.py --channel 1 --raw 294720 --therm 3344
```

Поле `status` в выводе этих инструментов говорит, можно ли верить числам:

| `status` | Что значит |
|----------|-----------|
| `ok` | всё посчитано |
| `no_temperature` | струна читается, термистор оборван — температурной поправки нет |
| `no_vw_signal` | `t01 = 0`, струна не отвечает |
| `disconnected` | нет ни струны, ни термистора — канал пустой |
| `unresolved_scale` | `t01` не лёг ни в один масштаб из `hz_min`…`hz_max` |

## Файлы

- `adl200a_mqtt.py` — демон;
- `calibration.py` — перевод сырых отсчётов в инженерные единицы (+ CLI);
- `live.sh` — живая консольная сессия для настройки и установки;
- `channels.py` — настройка каналов и собственной записи прибора по файлу;
- `ace_config.py` — поля `SCC`, полосы, коды типов, разбор файла настройки;
- `sensors.example.json` — шаблон настройки и калибровок по каналам;
- `docs/install-ace-1910.md` — инструкция установщика: ячейка ACE 1910/1911 и масштабы аналоговых входов;
- `tests/` — тесты и эмулятор логгера на псевдотерминале (`fake_logger.py`):
  `python3 -m unittest discover tests` (сквозные нужны pyserial и paho-mqtt);
- `ace.py` — CLI для одной ACE-команды (`ace.py GTT`, `ace.py MEA`, …);
- `sniffer.py` — низкоуровневый hex-пробник порта;
- `prestart.sh` — ставит RS-232-режим на Moxa UPort 1150 (на прочих портах — ничего);
- `adl200a.service` / `adl200a.default` — systemd-юнит + шаблон конфига;
- `install.sh` — установщик;
- `examples/subscribe.py` — пример MQTT-консьюмера.
